# ADR-006: Direção de Dependência (Hexagonal / Ports & Adapters)

## Status
Proposed

## Contexto
Hoje o `server.ts` importa diretamente de `src/domain/*`, e os handlers inline misturam regras de negócio, persistência (arquivo JSON), transporte (Express) e chamadas ao Google GenAI. Não há limite entre o domínio e os frameworks. Isso viola a regra de arquitetura "políticas internas não devem depender de frameworks, bancos, transportes ou mecanismos de entrega", tornando impossível testar regras de negócio sem o servidor e difícil trocar de transporte ou banco.

## Decisão
Adotar **Hexagonal Architecture (Ports & Adapters)** com direção de dependência estritamente para dentro:

```
                 Adapters (fora)
         Express | Drizzle/Postgres | GenAI | SSE
                     |  |  |  |
                 Ports (interfaces)
                     |  |  |  v
              Domain / Use Cases (centro, puro)
              - sem imports de Express, Drizzle, better-auth, vite, react
```

Regras:
- **Domain (`modules/<id>/domain/*.ts`)**: entidades, value objects, regras de negócio. Zero imports de framework/banco/transporte/UI.
- **Application / Use Cases (`modules/<id>/services/*.ts`)**: orquestram fluxos, transações, autorização, chamam ports. Não sabem de Express nem de SQL.
- **Ports**: interfaces definidas no domínio (ex: `AgentRepository`, `EventBus`, `AiProvider`).
- **Adapters (`modules/<id>/adapters/*.ts` e `app.ts`)**: implementam ports usando Express, Drizzle, GenAI, SSE. São a única camada que importa frameworks.
- **Bypassar use cases chamando repositories diretamente de controllers é um cheiro arquitetural**, a menos que documentado intencionalmente.

O kernel (`@nettoscorp/kernel`) define apenas o contrato `Module`; não importa Express.

### Alternativas consideradas
| Opção | Prós | Contras |
|-------|------|---------|
| A. Hexagonal / Ports & Adapters (escolhido) | Isola domínio, testa regras sem servidor, troca de framework fácil | Mais camadas/indireção (ceremonia) em domínios simples |
| B. Layered tradicional (controllers → services → repos) | Simples, familiar | Camadas se tornam pass-through; domínio vaza para infra |
| C. Sem camadas (status quo, monolito inline) | Zero custo inicial | Impossível testar domínio isolado; acoplamento total |

## Consequências
### Positivas
- ✅ Regras de negócio testáveis sem Express, banco ou rede
- ✅ Direção de dependência protegida: domínio não sabe de nenhum framework
- ✅ Troca de transporte (Express → Fastify/Cloudflare Workers) ou banco (JSON → Postgres) afeta apenas adapters

### Negativas / Trade-offs
- ⚠️ Mais arquivos e indireção para domínios CRUD simples (aceito porque o domínio TokenizAi tem regras de negócio: RBAC, clearance, orçamento, governança)
- ⚠️ Exige disciplina da equipe para não criar imports "por fora" das camadas

## Rastreabilidade
- Specialist rule: "Protect dependency direction"; "No architecture astronautics"
- `documentação institucional/05-ARQUITETURA-ALVO.md` (isolamento por design)
