# ADR-010: Comunicação Entre Módulos e Contratos Explícitos

## Status
Proposed

## Contexto
Com a arquitetura modular (ADR-004/005), módulos precisam se comunicar sem acoplamento direto. Hoje não há contrato entre módulos: `server.ts` chama tudo inline e acessa `db` (estado em memória) diretamente. Além disso, a integração com Paperclip (adapters, MCP, skill catalog) não tem camada de tradução — qualquer mudança no Paperclip quebra o TokenizAo.

## Decisão
Comunicação entre módulos via **contratos explícitos** e **barramento de eventos**, com **anti-corruption layer (ACL)** para sistemas externos:

1. **Barramento de eventos interno** (`SimpleEventBus` no kernel): módulos emitem eventos (`chat:message:created`, `task:delegated`, `governance:audit:written`) e assinam os de interesse. Nenhuma chamada direta entre módulos.
2. **Contratos explícitos**: interação síncrona entre módulos só pelo container DI (`di.resolve('nome.do.servico')`), com interface de contrato versionada. Nenhum módulo importa a implementação de outro.
3. **Anti-corruption layer para Paperclip**: o módulo `runtime` (e futuros adapters) traduz o modelo Paperclip para o modelo TokenizAo em uma camada de tradução, isolando o domínio de mudanças externas (ADR-003 reforça: adaptadores, não modelo unificado).
4. Nenhum módulo acessa o banco de outro módulo diretamente; dados cruzam apenas por contratos/eventos.

### Alternativas consideradas
| Opção | Prós | Contras |
|-------|------|---------|
| A. Event bus + DI contracts + ACL (escolhido) | Baixo acoplamento, falha isolada, fácil de estender/testar | Eventual consistência para fluxos assíncronos; exige disciplina de contrato |
| B. Chamadas diretas entre módulos (import de serviço) | Simples, síncrono | Alto acoplamento; mudar um módulo quebra vários |
| C. Message broker externo (Kafka/RabbitMQ) | Desacoplamento total, persistência de filas | Infra pesada para o estágio atual; overkill |

## Consequências
### Positivas
- ✅ Módulos são substituíveis e testáveis isoladamente
- ✅ Integração com Paperclip protegida por ACL (mudanças externas não quebram o domínio)
- ✅ Rastreabilidade de fluxos via eventos

### Negativas / Trade-offs
- ⚠️ Consistência eventual em fluxos assíncronos (aceito para notificações; transações críticas usam DI síncrono + banco transacional)
- ⚠️ Mais código de tradução (ACL) e contratos a manter

## Rastreabilidade
- ADR-003 (adaptadores, não modelo unificado)
- `documentação institucional/05-ARQUITETURA-ALVO.md` (Ledger & Reconcile, isolamento por design)
- Specialist rule: "Cross-context communication should happen through explicit contracts, events, APIs, or anti-corruption layers"
