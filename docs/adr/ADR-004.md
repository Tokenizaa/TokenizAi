# ADR-004: Interface de Módulo e Federação

## Status
Proposed

## Contexto
O repositório declara a Fase 5 (Module Architecture) concluída, mas não há nem contrato de módulo nem federação. O `server.ts` é um monolito de ~1.741 linhas (~68 KB) com handlers de rota inline agrupados por domínio (chat, org, tasks, runtime, projects, finance...). O frontend tem 17 módulos apenas de UI em `src/modules/*`, sem backend correspondente. Não existe interface `Module { routes, services, ui, migrations, config }`, nem carregamento dinâmico, nem registry de módulos. Sem esse contrato, não há como extrair domínios do monolito nem adicionar novos módulos sem mexer no `server.ts`.

## Decisão
Criar o contrato `Module` (pacote `@nettoscorp/kernel`) que todo módulo de negócio deve exportar no arquivo default de `modules/<id>/module.ts`:

```ts
interface Module {
  id: string;
  name: string;
  version: string;
  config: ModuleConfig;           // enabled, routePrefix, features
  dependencies?: string[];        // ordem de carga / inicialização
  routes?: () => ModuleRoute[];   // handlers de rota (adapter Express)
  services?: () => ModuleServiceFactory[]; // registro no container DI
  migrations?: () => ModuleMigration[];   // up/down ou SQL bruto
  ui?: ModuleUI;                  // lazy load React + navegação
  init?(container): void | Promise<void>;
  teardown?(): void | Promise<void>;
  health?(): Promise<{ ok; details }>;
}
```

O kernel (`@nettoscorp/kernel`) é framework-agnóstico: não depende de Express, banco, transporte ou UI. A fábrica `createApp({ modules })` carrega módulos dinamicamente via `import()`, ordena por dependências, registra serviços no DI, monta rotas sob o prefixo do módulo e executa migrações. Cada módulo é uma unidade independente de implantação dentro do monorepo.

### Alternativas consideradas
| Opção | Prós | Contras |
|-------|------|---------|
| A. Contrato `Module` + `createApp` (escolhido) | Padroniza módulos, permite carga dinâmica, isola falhas por módulo | Requer refatoração do `server.ts` e novo package kernel |
| B. Manter monolito + pastas de convenção | Sem mudança de código, zero risco imediato | Não resolve acoplamento; todo novo módulo edita `server.ts`; não há isolamento |
| C. Micro-frontends / Module Federation puro no frontend | Isola UI | Não resolve o backend monolítico; a Fase 5 exige server + UI |

## Consequências
### Positivas
- ✅ Módulos podem ser adicionados, removidos ou atualizados sem tocar no `server.ts`
- ✅ Carregamento preguiçoso (`import()`) reduz o tempo de inicialização e o bundle
- ✅ Falha de um módulo não derruba todo o servidor (isolamento de falha)
- ✅ Cada módulo declara suas migrações, serviços e rotas — autocontido
- ✅ Health check agregado por módulo (observabilidade)

### Negativas / Trade-offs
- ⚠️ Custo inicial de refatoração do `server.ts` (Strangler Fig, veja ADR-005)
- ⚠️ Rotas são o único ponto onde o servidor web "vaza" para dentro do módulo (aceito deliberadamente — ver ADR-006)
- ⚠️ Em produção, módulos `.ts` precisam ser empacotados/pré-buildados antes do `import()`
