# ADR-005: Refatoração do `server.ts` para carregamento dinâmico de módulos

## Status
Proposed

## Contexto
O `server.ts` é um monolito Express de ~1.741 linhas (~68 KB) com:
- estado em memória (`/tmp/nettoscorp-tokenizai-db.json`, `structuredClone` de `INITIAL_ENTERPRISE_STATE`);
- barramento SSE inline (`sseClients`);
- handlers de rota inline agrupados em seções de domínio (`/api/chat/*`, `/api/org/*`, `/api/tasks/*`, `/api/runtime/agents/*`, `/api/projects/*`, etc.);
- imports diretos de `src/domain/*` e `src/types/enterprise.ts`.

Qualquer mudança de domínio exige editar esse arquivo, gerando conflitos de merge e risco de regressão. Não há separação entre transporte (Express), regras de negócio e persistência.

## Decisão
Refatorar `server.ts` usando o padrão **Strangler Fig**:
1. Criar `app.ts` com a fábrica `createApp({ modules })` (kernel) que monta módulos dinamicamente.
2. Criar `@nettoscorp/kernel` com `ModuleLoader`, `DiContainer` e `SimpleEventBus`.
3. Extrair cada bloco de domínio de `server.ts` em um módulo sob `modules/<id>/` com a interface `Module` (ADR-004):
   - `gateway` — `/api/health`, `/api/events/stream`, `/api/bootstrap`, `/api/state/reset`
   - `chat` — `/api/chat/conversations`, `/api/chat/messages`, `/api/chat/inter-agent`
   - `org`, `tasks`, `runtime`, `projects`, `finance`, `commercial`, `marketing`, `products`, `customers`, `people`, `operations`, `agency-library`, `team-composer`, `operational-agents`, `governance`, `admin`
4. Mover a lógica de negócio dos handlers inline para `modules/<id>/services/*.ts` (use cases) e entidades para `modules/<id>/domain/*.ts`; manter handlers apenas como adaptadores Express.
5. `server.ts` se torna um ponto de entrada fino: `createApp({ modules }).then(app => app.listen(PORT))`.
6. Feature flag `MODULES_ENABLED` para alternar entre monolito antigo e novo app durante a transição; manter `server.legacy.ts` como rollback.

### Alternativas consideradas
| Opção | Prós | Contras |
|-------|------|---------|
| A. Strangler Fig + `createApp` (escolhido) | Zero downtime, rollback imediato, migração incremental | Dupla manutenção temporária (monolito + novo app) |
| B. Big Rewrite (reescrever `server.ts` de uma vez) | Limpo de imediato | Alto risco, longo período sem entregas, regressão provável |
| C. Apenas adicionar pastas sem tocar no `server.ts` | Sem risco imediato | Não resolve o acoplamento; módulos ficam órfãos |

## Consequências
### Positivas
- ✅ `server.ts` deixa de ser um gargalo de ~68 KB; cada domínio vive no seu módulo
- ✅ Rollback imediato via feature flag / `server.legacy.ts`
- ✅ Testabilidade: serviços de domínio podem ser testados sem subir o Express

### Negativas / Trade-offs
- ⚠️ Período de convivência de duas implementações (dupla manutenção) até a remoção total do monolito
- ⚠️ O estado em memória JSON precisa ser migrado para PostgreSQL/Drizzle por módulo (ADR-009) antes de considerar produção
